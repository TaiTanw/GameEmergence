## `V_4`：箱体方向可移动性（目标与当前接触策略）

以下三项是 `V_4` 的验收目标；当前代码仅完成其中的方向传播、接触施力过滤和同向被动速度抑制，位置与移障时序仍待收束。

1. **先定时序与读口。** 相位 1 保存直接墙/支撑几何事实；相位 2 只派生这些事实能确定的静态方向限制。相位 4 在当前接触策略中结合箱间接触、环境允许位移与末箱抵墙结果，形成**本帧最终方向可行性**。不把上帧箱链阻挡冒充本帧相位 2 的几何事实，也不把“碰到箱子”直接等同于“失去自由度”。先限于水平左右方向，不引入通用约束矩阵。
2. **让结果真正被消费。** 阻挡方向应影响该方向的接触偏置分担、推力登记与残余速度清理；障碍移开或反向时，同帧或下一物理帧应解除限制。实体只读出口需注明何时可信，避免表现层提前读相位 2 的静态部分并误认为完整箱链结果。
3. **验收。** 单箱左/右抵墙、两箱与三箱末箱抵墙、障碍移开、反向退出；记录每箱请求与下一步实测，确认卡墙时不继续向墙内登记速度，解锁后不释放积速。单向平台和可通行坡面不因左右限制被错误锁死。

`V_4` 的**结果时序/数据含义**属于可复用框架边界；“怎样沿箱链传播阻挡”属于 `CurrentAabbContactSolver` 的具体有限策略，并与 `K_2` 共用场景。现在不应只给 `BasePhyFunData` 加一个永久 `canMove` 布尔值来代替相位 4 的链式判断。

### 速度清理与施力登记（立项时核对）

`ClearTransientSpeedForFinalBlock` 继续用 `phyHSpeed` 作门闩。`phyHSpeed` 是相位 3 写入的净被动水平速度；`ClearTransientSpeedAtWall` 清的是限时速度和动态力累计，主动 `horizontalSpeed` 下一帧仍由输入重算。总速度（`GetPlanarVelocity` 的水平分量）会把「主动走进墙」算进清速条件。箱子当前没有主动水平速度，两条门闩对箱子几乎相同；改成总速度并不补上箱链缺口。

静墙对**本帧位移**的裁剪在 `CurrentEntityRequestSolver.FinalizeRequest`：请求 X 短于候选时写下 `blockedHorizontalDirection`。`ClearTransientSpeedForFinalBlock` 发生在这之后，只按该方向清瞬时速度库存。`ApplyPendingContactForces` 经 `SetOrUpdateDynamicForce` 把可行接触写成下一帧的 `apply` 施力。接触减速在另外两处：新接触的 `ApplyPendingAttenuations`，以及退出后 `RemoveForce` 转入 `fadeAway`，再由地面消退倍率削 `speedStacking`。

`FinalizeRequest` 每次环境回算都会按**该实体自己**的裁剪重写 `blockedHorizontalDirection`。残余回算结束时、中间箱在方向传播之前仍只带有自己直接受静墙裁剪的结果；传播后才可能获得末箱的阻挡方向。

### 本次代码单元

本次结构变动等级 1：未新增类或改动 0→5 相位槽；在残余回算结束到施力收集之间加入有界水平传播。以下状态按当前代码和定向验证记录。

| 单元 | 闭环 | 落点 |
|---|---|---|
| `V_4.1` | 末箱已被静墙裁剪后，沿当前水平接触把同一方向写给后面的箱子和玩家，并赶在 `PlanContactEffects` 之前 | **方向传播已在两箱、三箱定向夹具核对；位置闭环未通过。** `CurrentAabbContactSolver.PlanPropagatedHorizontalBlocks` 用预测框判断左右推挤，`PhysicsSolverMgr` 在残余回算之后写回 `blockedHorizontalDirection`，不覆盖直接裁剪；这一时点已无法改变本帧偏置和请求 |
| `V_4.2` | 该限制进入推力登记和退出清理：顶住时不向墙内登记 `apply`；障碍移开或反向后下一物理帧解除，不放出已清掉的累计 | **同向 `apply` 抑制已落地，移障时序仍需收束。** 施力登记与相位 4 清理沿用现有读口。`EntityEffectState` 在相位 3 用上一帧阻挡方向清零同号累计；移障当帧相位 3 仍读旧方向，下一帧相位 3 才恢复同向被动施力。持续状态速度未改 |

验收仍放在整个 `V_4`：两箱、三箱末箱顶墙时既看方向，也看每对实体的最终请求间距和下一步实测；单向平台、可通行坡面及单箱直接顶墙作回归。方向写回或单箱场景通过，不等于箱链位置已通过。

### 本轮编辑器验证与未闭环点

使用 Unity 2022.3.54f1c1 的临时项目副本运行现有检查：Edit Mode 环境接入 **148 项通过**；`SlopePushSceneChecks.RunForBatch` 两组各 540 个 Dynamic 物理步通过。后者是单箱上坡、受阻、松手和反向回归，不覆盖本轮箱链问题。临时夹具没有写入仓库，也不运行输入 FSM 或表现层。

定向夹具把玩家侧推动者、两箱或三箱摆成水平链，初始相邻交叠约 `0.001`，每个实体本帧向墙请求 `0.08`，末箱贴墙。两箱、三箱的末箱阻挡方向均传播到上游；移开墙后，本帧相位 4 的方向均归零。但两箱的末端请求仍交叠约 `0.041`；三箱的首对和末对请求分别交叠约 `0.040`、`0.041`，推进一次 Unity Dynamic 后末对实测交叠约 `0.047`。当前策略的 `ContactSlop` 是 `0.002`。这说明方向传播不等于本帧位移请求已分开；在真实场景还须核对引擎修正与可见表现。

另一个定向检查模拟移障：同向 `apply` 在移障后的第一帧相位 3 仍因上一帧阻挡方向得到 `phyHSpeed = 0`，相位 4 才把方向改为 0；第二帧相位 3 才重新积分。反向施力不走同号抑制分支。这里说的是**同向被动施力**，主动输入速度仍按原规则计算。

## `P_2`：基础推箱紧跟、松手停止（当前玩法策略）

1. **先定位滑行来源。** 在平地单箱的按住、松手、反向三个区间同时记录玩家/箱子的预测、最终请求、`EntityDisplacementObservation` 实测、接触来源状态及刚体速度。区分“策略仍请求箱子前进”和“请求已停但 Unity 实际仍移动”，再决定是否需要碰箱体阻力/刚体参数。此检查不需要深究完整求解器。
2. **将基础推动收束到当帧位移。** 优先在 `CurrentAabbContactSolver` 的具体方法内调整持续推箱策略：按接触偏置与有效输入形成当帧共同位移，停止输入后不再由该推箱接触留下前进速度；其它环境力的通用 `EntityEffectState` 语义不随之改变。保持现有查询/提交入口和相位顺序。若 Unity Dynamic 实测仍滑，再对该执行端做最小的箱体专属处理，不能仅靠增大共享阻力掩盖原因。
3. **箱链共同减速。** 平地 1、2、3 箱必须近似一起前进；箱数增加时整链速度单调降低，玩家与接触箱不持续穿入或拉开。现有两两 `EnvImpact` 分配只能作为起点；若不足，在当前策略内补一个有界的水平箱链共同位移决定，不扩成通用刚体求解器。可通行坡面、多箱上坡与任意长链的完整传播仍由 `K_2` 后续承接。
4. **验收。** 视觉上推多少跟多少，允许约一个物理帧误差；松开后箱子无可见继续滑行；受阻、反向与再推动稳定。核对箱链整体减速，并保留现有 Dynamic、单向平台和单箱斜坡回归。

`P_2` 是**具体推箱手感**，即使改动位于物理策略代码，也不等于扩大 K9 框架接口。未来“靠近交互后才可推、反向可拉”另属玩家能力/交互规则：交互对象可作为拉动锚点，但不能把整条箱链的推力传播限定为只处理这个对象；本轮只保留该边界，不实施交互开关或拉动。

## 当前顺序与人工核对入口

`V_4.1`、`V_4.2` 已写入代码；下一步先核对并收束箱链请求间距与移障时序，再考虑 `P_2` 的共同位移和手感。读[数据流图第一页](物理框架调度与数据流.drawio)时，从 4.3 残余回算走到 4.4 方向传播、4.5 接触效果；第二页看阻挡方向跨到下一帧相位 3 的读写时间。

`PlanResidualOffsets` 在传播之前，箱链方向进不了本帧接触偏置。原条目里的「偏置分担」不在已落地的 `V_4.1` / `V_4.2`；定向夹具已经显示两轮残余没有把两箱、三箱末箱抵墙的请求位置完全分开。

人工 Play Mode 建议从 `TeskScenes1.unity` 和菜单 **自定义工具 → EPhy 实时数据显示**进入：先选玩家，再逐个选箱子；在单箱、两箱、三箱末箱抵墙、移障和反向的连续物理步中，按 `Fixed Tick` 记录“接触对偏置”“最终请求位移”“MovePosition 目标”，并在下一步对照“实际位置”“引擎修正量”。对相邻两实体，用各自目标中心距与碰撞框半宽之和核对**请求终点交叠**；窗口的“原始重叠深度”是预测接触深度，不能替代该计算。窗口的“环境阻挡 X”只给布尔值，现码也会对传播阻挡置真；若需区分左右方向或检查 `phyHSpeed`，在 `BasicEntity.BlockedHorizontalDirection` 与 `UpdatePassiveEffectSpeed` 处逐帧观察。再复测单向平台和可通行坡面没有被左右锁住。结果按请求、下一步实测和视觉表现分别记录。

`V_4.1` 已写回现有 `blockedHorizontalDirection`。链上每个还没被静墙裁到的箱子，以及玩家，都会得到末箱的方向。接触判断用的是预测框：残余回算可能已经把上游箱子推开，若改看请求终点，这条推挤会丢。

验收放在 `V_4` 结束，不把方向传播单独视作位置闭环。现有清速范围如下：

- `ClearTransientSpeedForFinalBlock` 在净 `phyHSpeed` 朝阻挡方向时，清该实体全部限时速度和动态累计。接触退出时的 `ClearBlockedContactSpeed` 只清接收者身上、且朝阻挡方向的那一条接触来源。新接触的 `AttenuateTransientContactSpeed` 只削弱限时速度和 `fadeAway`，不动 `apply`。
- 推的一方自己的冰面来源不在接触退出清理里。当前 `V_4.2` 在下一帧相位 3 读取上一帧阻挡方向，抑制同向 `apply` 并清掉该来源累计；反向来源仍按原规则积分。
- 持续状态速度不在这三条清理里。当前冰面 `phySpeed` 为 0。

持续顶墙时，同向被动 `apply` 已被抑制；移障当帧相位 3 仍读旧方向，恢复时点须按前述连续物理步核对。主动输入速度仍独立计算。

### 冰面被动速度

当前冰面预制体 `Idex = 15`、`maxISpeed = 2`、`speedChangeNum = -0.5`、`phySpeed = 0`。箱子没有 `ICanMove`，冰面动态力平衡速度是 0，`FixUpdate` 每帧把箱子的冰面 `speedStacking` 夹回 0。玩家按住方向时，冰面来源保持 `apply` 并按 `Idex` 累加；顶墙期间的同向累计被 `V_4.2` 抑制。障碍移开首帧因仍读旧方向不会立即恢复这一项被动速度。`speedChangeNum` 仍只改主动速度倍率。

平地推箱紧贴目前由脚下 `BaseGround.slowingEffect` 承担，不写入箱链方向。`P_2` 余下的当帧共同位移和 1–3 箱共同减速仍后置。同速不再登记新推力，也不在这两个单元里。
