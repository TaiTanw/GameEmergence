# K_9：解算边界收束

2026-10-03 · `K_9.1–K_9.5` 已完成。本文件记录边界与验收。优先级和状态以[待办安排](../待办安排.md)为准；既有相位与数据语义以[工程原则](../工程原则.md)和现码为准。

## 目标与现状

人工应能从数据职责、计算归属、读写时序及适用范围判断当前解算器能做什么、结果何时可信、替换解算策略或物理执行端从哪里进入，而不必逐行理解接触和坡面算法。保留已验证的单箱场景行为；不借 K9 完成多箱链、统一二维速度、全 Kinematic、第三方引擎接入或具体游戏规则。

| 现有数据 | 所有者、产生与有效期 | 消费与边界 |
|---|---|---|
| `EntityMotionFrame` | `BasicEntity.motionFrame` 在相位 3 的 `SpeedCalculation/BuildMotionFrame` 整体替换；值另复制进预测框，同一物理帧内只读。 | 预测位置、相位 4 的接触读速和请求合成读取它；平台携带参与位置，不参与自身接触施力。它不含碰撞纠偏、跨帧累计或实际落点。 |

| `EntitySolutionResult` | `BasicEntity` 持有；上一帧相位 4 写下的阻挡方向先供下一帧相位 3 汇总被动速度，随后 `PositionPrediction` 重置偏置、环境修正、请求和方向。相位 4 累加偏置、反复改写请求；环境裁剪写直接方向，残余回算后接触策略可写传播方向。`allowedHorizontalDelta` 由每次候选查询初始化。 | 管理器读请求终点与阻挡方向以回算和登记效果；相位 5 只读最终 `requestedWorldDelta` 提交。传播方向不回写已完成的残余偏置或请求；请求不等于 Unity 实际落点。 |

四类数据是**职责边界**，不是四次不可回访的线性阶段。当前读写链为：`BuildMotionFrame` → 预测上报 → 接触策略给出实体对偏置 → Unity 端查询候选环境、实体请求策略合成请求 → 受阻时有限轮回算并重查 → 沿预测水平接触传播阻挡方向 → 登记下一帧接触效果 → Unity 端提交一次 `MovePosition` → 后续物理更新后的实际落点。方向传播在残余回算之后，不重算本帧偏置和请求。

## K_9.2 完成记录：接触效果决定与应用

`PhysicsSolverMgr.ApplyContactEffectsAfterFinalRequests` 在最终请求和反馈轮结束后执行。它先形成有向力参数、新接触衰减及退出关系的当帧决定，再按原顺序调用实体：静墙速度清理 → 刷新有向力 → 应用衰减 → 来源级清理与 `RemoveForce`。有向来源键仍是施力实体；`previous/current` 的比较及交换仍决定首次接触与退出，接收者的累计数值仍在 `EntityEffectState`。效果在相位 4 写入，下一帧相位 3 积分；`EntitySolutionResult` 仅承载本帧位移请求，不承载接触效果。推力公式、尾效规则、反馈次数与 Unity 提交时机未改。

## K_9.3 完成记录：请求与后续实测

`EntitySolutionResult` 承载相位 4 的位移请求与阻挡方向，不承载 Unity 实际落点或接触力累计。`BasicEntity` 在相位 5 向 Unity 提交一次 `MovePosition` 时保存请求起点、请求位移和实体物理步编号；下一次相位 1 在几何查询前读取 `Rigidbody2D.position`，发布只读的 `EntityDisplacementObservation`。读取者可把该实测落点、实际位移与原请求对应，不会把提交时的目标当作已到达位置。禁用或重新启用实体会清除待观察请求和旧结果。

结果的 `DifferenceFromRequest` 是“后续实测位置减请求目标”，可能包含其它脚本的位置写入；它不单独证明 Unity 碰撞修正。手动驱动物理相位时，须在提交与下一次采样之间推进模拟。此单元只做离线 C# 编译及静态边界检查；按本轮约定，完整编辑器回归留到 K9 全部完成后。

## K_9.4 完成记录：Unity 查询与提交入口

`IPhysicsWorldAccess2D` 与 `UnityPhysicsWorldAccess2D` 集中当前后端的 AABB/刚体位置读取、BoxCast/OverlapBox/OverlapCollider、碰撞层与忽略碰撞查询，以及一次 `MovePosition` 提交。`BasicEntity.PhysicsWorld` 是可覆写的接入点；角色与箱子的相位 1 接触和区域探针、相位 3 预测框、相位 4 候选环境查询和相位 5 提交都经此入口。`EntityDisplacementObservation` 也从此入口读取下一相位的实际位置。查询与提交端只执行 Unity 调用，不计算偏置、坡面或推力。

该接口保留 `Bounds`、`Collider2D`、`RaycastHit2D`、`Rigidbody2D` 等 Unity 类型，是**当前 Unity 2D 后端的窄口**。它覆盖本物理模块的实体查询与提交；输入选取等其它模块仍可直接使用 Unity 查询。接入其它物理系统时需在此处转换形状和命中数据；`PhysicalBoundingBox` 当前仍是 AABB 且携带 `BasicEntity`，不宣称已具备跨引擎中立数据。此单元只做离线 C# 编译（0 错误，沿用现有 `System.Net.Http` 警告）；完整编辑器回归留到 K9 完成后。

## K_9.5 完成记录：策略入口与相位协调

`PhysicsSolverMgr.ContactForSolution` 仍是相位 4 的协调入口：清理当帧工作区 → `IContactSolveStrategy.PlanInitialOffsets` → 调实体累加偏置 → 逐实体查询环境并形成请求 → 按策略给出的上限执行残余水平反馈，每轮结束重查环境 → `PlanContactEffects` 给出可行的有向力参数 → 管理器维持 `previous/current` 关系并按“静墙速度清理、写力、衰减、退出清理”的顺序应用效果。具体 `CurrentAabbContactSolver` 保存现有 AABB 最小重叠轴、`EnvImpact` 权重、闭合速度和力参数公式；策略接收整帧预测集合，未来可在同一入口协调多实体，但当前仍为两两扫描和最多两轮反馈。

`BasicEntity` 仍拥有 `EntityCandidateGeometry` 工作区，通过 `IPhysicsWorldAccess2D` 查询并过滤环境命中，再调用 `IEntityRequestSolveStrategy.ResolveCandidate`。最终请求由 `FinalizeRequest` 合成；具体 `CurrentEntityRequestSolver` 保存现有坡面抬升、墙面限位、单向平台和撞顶裁剪公式。它若需补查坡面或抬升路径，仍通过独立 Unity 查询端，不直接提交刚体。两种策略只返回当帧决定；实体数值状态、接触关系、相位和下一帧积分仍由原所有者维护。

替换位置因此分为两处：改变接触/坡面算法时替换策略实现；改变 Unity 查询或位移提交时替换物理世界入口。当前 `PhysicalBoundingBox`、环境命中和策略输入仍带 Unity 与 `BasicEntity` 类型；这些是现行 Unity 2D + AABB 适用范围，不是完整刚体求解器或第三方后端适配完成的声明。K9 实施期间冻结推箱可见行为，本单元未改权重、给箱子的速度、摩擦力或玩家交互规则；现已将后续方向受限与停止滑动列入[独立待办](V_4-P_2-推箱方向约束与停止滑动.md)。

前两页[物理框架调度与数据流图](物理框架调度与数据流.drawio)对应最终入口：第一页是相位 4 的管理器、两种策略与独立 Unity 端的调用方向；第二页是数据所有权、当帧决定、T+1 实测和效果状态的读写。最终统一检查：运行时与编辑器脚本离线编译均为 0 错误；Unity 批处理 1080 个 Dynamic 场景物理步、148 项环境检查，以及两次进出 Play Mode 的 46 项观测检查通过。场景回归还逐帧核对了下一次相位 1 的请求/实际落点对应关系。编辑器初次导入新脚本曾触发一次临时缺失类型编译，导入完成后重跑无错误；测试产生的 ProjectSettings 序列化变化已还原。可见手感仍需在人工 Play Mode 中观察，自动检查不作手感结论。

## V_4 当前增量与核对边界
