## P27 已核对范围与评估

P26 已提交为 `c054e17`，关序 JSON 纯缩进调整单独提交为 `709f4ca`，语义一致。2026-10-18 P27.1 逻辑经人工核对，三状态示例也已确认，用户授权入工程。本轮只完成认知条样式；迷雾、其它页面动画与指南沿后续单元推进。[确认示例](待办具体事务文档集中/P_27-认知条预览/认知条-确认示例.png)与[工程预览](待办具体事务文档集中/P_27-认知条预览/认知条-金框紧凑版.png)保留供对照。

已确认的视觉方向：探索结束后的「认知降费购买」「本场体能效果」两页使用深蓝色流动迷雾显现、白色文字；其余界面沿现有纸样统一动画与细节。保留原有两页顺序、购买和一次性抽取／锁存规则，动画只表达流程结果。

已确认的长按规则：长按结束只提供确认，不扣除或返还认知。以本关初始认知为满条，表达为 `T = max(0.2秒, 2秒 × 当前剩余认知 / 本关初始认知)`：满条2秒、半条1秒、10%及以下0.2秒。取消原左上「长按回车结束探索」便签框。白色部分表示真实剩余认知，内部黑色尺状刻度表示回车确认剩余量，两者均从两侧向中心缩减；认知消耗区域保留金色外轮廓，黑色刻度消失后不留描边。两端为外尖较长的四棱星，中央固定空心菱形。余额数字及自然耗尽仍沿原规则与入口处理。

每次按下时锁定目标时长，黑色刻度范围仍随实时余额比例变化；松开沿现有0.2秒回填取消贡献。暂停、文本输入、换页／过场和输入停用继续取消长按，恢复后须松手再按。工程用单个局部原生 UI 绘制组件复现已确认的几何样式，以便缩放时保持星角、空心孔和刻度；组件只读比例，不另建余额或计时。

本轮按用户实景反馈将边框及中央菱形换成金色，条高80改40、上移12布局像素；1920基准下计入描边与原背包按钮约留9像素，960画幅约4.5像素，按钮原位置和大小保留。19项绘制检查及间距核对通过，资源包重建完成；此前228项流程回归仍为逻辑验证基线，本轮只改局部颜色和布局。

用户已授权认知条局部叠加柔光，现已接入：同一绘制组件在白底下方增加一个柔光四边形，共用专用 UI 材质；颜色、强度与半径固定，只有有效长度随白色剩余认知向中心缩小，零认知时不生成柔光。金色固定外框不参与柔光范围，黑色回车刻度与中央透明孔保留。默认强度0.75、最大外扩6布局像素，计入描边后与背包按钮保守仍留约3布局像素；不新增相机、运行时材质实例或离屏缓冲，不改变认知与长按逻辑。[工程预览](待办具体事务文档集中/P_27-认知条预览/认知条-局部柔光.png)。

本轮30项绘制与兼容性检查通过，含1920／960原生像素差分、恒定亮度、影响面积收缩、零认知残留、中央孔、黑线、RectMask2D、Stencil Mask和CanvasGroup淡出；1920画幅满条／半条实际受影响像素13956／7040，960为3472／1768，两画幅同位置亮度差均为0，耗尽后受影响像素为0。按钮间距及Shader编译检查通过，StandaloneWindows64资源包已重建。实际关卡与Windows实包观感仍待人工核对；这是局部 UI 显示反馈，未扩展场景灯光。

建议推进顺序：先做 P27.1 的确认行为与 P27.4 的说明，避免删除便签后玩家失去入口；再以两页菜单完成 P27.2／P27.3 的视觉样板，最后推广 P27.5。样板和整合分别验证，完成后重建相关 Addressables。

文字发光的技术判断：可行。现有文字本来就是独立 UI 组件，适合将背景雾、白字与柔光分层。一个 Canvas 并不是一张可直接指定材质的整屏图，给背景套 Shader 不会自动识别或提取文字。推荐先用文字自身的 SDF 材质实现柔光；Unity 的 [TMP 距离场材质说明](https://docs.unity.cn/Packages/com.unity.textmeshpro%404.0/manual/ShadersDistanceField.html)描述了 Glow／Underlay，项目本地 TMP Shader 也已核到相应属性。这里引用其效果原理，不据此升级现有 TMP 版本。

若坚持“单独渲染整层文字 → RenderTexture → 模糊／Bloom → 合成”，技术上也可做，但复杂度提高到中高，增加纹理带宽、画幅适配、遮罩边界和层级管理；不纳入首版默认方案，需另行核对。仅降低整组透明度也不会自动停用点击，动画必须同时管理交互和射线阻挡，参见 [CanvasGroup 官方说明](https://docs.unity3d.com/2022.3/Documentation/Manual/class-CanvasGroup.html)。

验收重点：满认知2秒、半认知1秒、低认知最少0.2秒；白线不超出实际认知填充且不改余额；松手／暂停／过场取消；自然耗尽只进入一次准备；两页切换与退出不重复授予效果；暂停中雾和菜单动画可正常结束；中文不缺字、不溢出、柔光不糊字；指南按键与当前绑定一致、运行中无改键入口；小画幅与 Windows 实包的清晰度、遮挡和 GPU 开销复核。

## 暂放：关序随机槽（P17）

最低边界：关序配置能明确区分固定线性关与随机组；两者都走同一个通关、向量确认与进度入口。此区分属于关序配置，不放进角色或教学／探索阶段。随机组沿原范围：打乱后把组内全部场景打完，不默默改成只抽一关。

后续主方案：窗口明确区分「固定关」与「随机组」。固定关填写一个场景，随机组填写多个固定制作的场景；新局开始时一次打乱各组，展开为实际场景序列。例如固定 A → 随机组 B／C／D → 固定 E，生成 A／D／B／C／E，仍须打完组内全部场景。

存档只增加实际场景序列，沿现有当前序号推进。返回菜单、死亡和重进沿已保存路线，不重抽；旧场景名数组按固定关读取。开工时核对制作配置变化与旧路线兼容性，不能借不兼容自动重抽。

P16 先保持线性侧为场景名数组，结局另起列表。P17 再改线性侧。两处共用一份顺序文件、一份进度文件，不开第二份存档，也不预先做通用槽框架。进度里新增字段的版本到开工时一起定。

与 P16 的交界：通关沿展开的实际路线进入下一张场景，路线走完才查询结局；每次道具领取仍按 P16.1 叠加向量。

| 单元 | 要做成什么样 | 复杂度 | 风险 |
|---|---|---|---|
| P17.1 配置区分 | 窗口提供固定关／随机组；各场景在构建中启用，旧文件按固定关兼容 | 低至中。只扩制作格式，不扩阶段或角色 | 配置必须明确区分，不能靠运行时猜测 |
| P17.2 路线展开与持久化 | 新局一次展开实际路线，与当前序号存在同一进度；按单一序号推进，退出／失败／重进不重抽 | 中。省去行号、行内位置与分组运行状态 | 后面的组也提前确定；若将来动态解锁候选须重新评估 |

同一场景出现多次时，按场景名可以重复进入。工具先允许，若要禁止再改窗口校验。

这一主方案总复杂度中，人工仍可按组配置，运行时保持现有单一序号。收益是少一组运行状态与恢复分支，代价是未进入的组也提前确定。当前候选为固定制作时采用它；动态解锁不在本轮范围。P16 不提前实现随机路线。

阅读入口：`LevelOrderWindow`、`LevelOrderFile`、`SceneChangeMgr.TryClearLevel`、`DataAndInitMgr.LoadLevelIndex`。
